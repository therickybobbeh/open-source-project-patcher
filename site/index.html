Field guide

The open-source images we run, rebuilt with their vulnerable dependencies fixed.

support-images takes each project's upstream release, bumps what is vulnerable within a policy, runs the project's own tests, patches leftover OS packages with Copa, and signs what it publishes. Every rebuild starts as a pull request that a person reviews and merges.

What it does

Most CVEs live in the code an image ships

Copa patches OS packages in place. The Go modules, npm packages, jars and bundled tools inside an image only change when it is rebuilt from source, so that is what this pipeline does, with Copa as its last step.

Where the vulnerable code isCopa alonesupport-images
OS packages (apt, apk, rpm)patchedpatched, by Copa after the rebuild
Go modules, npm, pnpm, yarn, Maven, Gradle, Python, Cargonobumped in the source, rebuilt
Go standard librarynorebuilt with a fixed Go release
Bundled tools (helm, kustomize, git-lfs, gomplate, credential helpers)norebuilt from their own source and swapped in
Jars inside a bundled Java distributionnoswapped for the fixed release, pinned by sha256
Proof the result still worksnoneupstream's own test suite, plus smoke tests

How it runs

From an upstream release to a signed image

Each job either runs upstream's code or holds credentials, never both. Building or testing a project runs its code with root on the runner, so those jobs get nothing worth stealing. Select a step for what it does.

Life of a fix

One fix, from publication to production

A real case from Dex v2: golang.org/x/net v0.62.0, which fixes CVE-2026-78661 in the v0.60.0 Dex ships. Days count from the fix's release.

Bump rules

What decides a bump

Every rule shows up in the patch PR. A finding that stays has a reason, and the reason says what to do.

The smallest fix, within policy

The smallest fixed version above the installed one, the same minor first. The default policy allows minor bumps; anything bigger waits for a person.

needs-human: fix requires a bump beyond the `minor` policy

Seven days old

A fix version must have been out for 7 days, because hijacked releases are usually caught within days. CRITICAL fixes and CVEs on CISA's Known Exploited list go in at once. The nightly rescan picks the fix up once it clears.

cooldown: v0.62.0 released 1 day(s) ago (eligible 2026-11-03)

Releases, not commits

When an advisory names a commit as the fix, the bump waits for the first release tagged after that commit.

untagged: the fix (v0.58.1-0.2026…) is a commit, not a release

Never a withdrawn release

A version npm marks deprecated, or PyPI or crates.io yanked, is replaced by the next release that stands, whatever the severity.

lodash 4.18.0 was withdrawn … 4.18.1 considered instead

Holds and overrides

A recipe can hold a package (never bump it, or not past a version) or force a minimum version everywhere, each with a written reason.

held: helm 3's registry login fails with oras-go 2.6.1+

Upstream's tests decide

Every patch set runs the project's own suite. Failures upstream already had are re-run on the unpatched source and don't block; a skipped test needs a reason, an owner and an expiry.

✅ passed in 12.4 min — make test-local

No known-malicious versions

Bumped versions are checked against malicious-package advisories, and test setups only install releases older than the same 7-day cutoff.

⛔ Malicious-package advisories for bumped versions

The release gate

Rego rules (Open Policy Agent, through conftest) judge each image's final scan. They only report for now; with enforce on, a denied image is never signed.

Release gate (reported only (`gate.enforce: false`))

Policies

Every decision is a file in the repository

The bump rules above are settings, not code. Each one lives in a reviewed file; change it in a PR and the next run follows it. Two of them are Rego (Open Policy Agent, run with conftest, tested in CI): the release gate judges an image's final scan, the merge policy judges a patch set before the daily round merges its PR.

  1. Check whether it's covered
    Add the image to inventory.yaml and run the coverage
        check. It names the patched image to switch to, a missing release line, or no recipe.
    
        
    uv run --project patcher patcher coverage
    2. 
      
  2. Draft the recipe
    From the source repository, or from the image alone for a vendor image. The
        draft detects the release line, ecosystems, toolchains, Dockerfiles and test commands.
    
        
    cd patcher && uv run patcher init owner/repo --image quay.io/org/app:1.2.3
    3. 
      
  3. Resolve the TODOs
    One line per version you run, only the ecosystems that ship, the image you
        run today as the "before", smoke commands, and the test command upstream's CI uses. Then validate.
    
        
    uv run --project patcher patcher validate
    4. 
      
  4. Run it locally, as CI does
    Inside the patcher image, which never pushes. The report it writes
        is the PR body you'll review.
    
        
    scripts/patcher-docker.sh run <name> --out out   # out/<name>/<line>/generated/report.md
    5. 
      
  5. Make the first run clean
    Three things the report may ask. Tests that also fail on the
        unpatched source are upstream's: a test that needs live credentials or an external service goes in
        skips/<name>.yaml with a reason, an owner and an expiry — never one that fails only after the bumps.
        Findings in bundled artifact become a component or bundledJars. What stays fixable is acted
        on, or settled with VEX (Policies). Repeat until the run ends success, or
        tests-preexisting with every failure understood.
    6. 
      
  6. Open the PR, then merge what follows
    The recipe, its skips, any patches/<name>/,
        and the inventory entry. Merging starts the first patch run; merge its patch PR to release, then the record-release PR.
    7.

Terms

      
The words you'll meet

    

    

      
Recipe
recipes/<project>.yaml: where the source is, which lines to follow, how to build and test it.

      
Line
One version stream a recipe follows, such as v3.4: always its newest upstream tag.

      
Patch set
What a patch run produced for a tag, under generated/<project>/<tag>/: deps.patch, the plan and the report. Releases rebuild exactly this.

      
Revision
The .N in -patched.N. Each release or Copa refresh of the same upstream tag takes a new one.

      
Component
A third-party binary an image bundles, such as helm in Argo CD, rebuilt from its own source and swapped in.

      
Copa refresh
A new revision with only OS packages patched, no rebuild. The rescan starts one when only OS packages need fixes.

      
VEX
A recorded decision about a finding we can't or needn't fix (vex/<project>.yaml), published with each image as OpenVEX.

      
State
state/<project>/<line>.yaml: what is released now, with digests and the findings known at release.

      
Release-age rule
The 7-day wait before a fix version is used (minReleaseAgeDays). PRs call it a cooldown.

      
needs-human
A fix the policy won't apply on its own. Raise the policy, add an override or a patch, or record a VEX decision.
